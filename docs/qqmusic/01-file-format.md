# 01 - mflac/mgg 文件格式分析

## 1. 文件结构总览

QQ 音乐下载的 `.mflac` 文件（VIP 下载目录 `%USERPROFILE%\Music\VipSongsDownload`）
结构如下：

```
+---------------------------------------------------------------+
| 加密的 FLAC 音频数据（XOR 流加密）                              |
+---------------------------------------------------------------+
| 192 字节下载器附加元数据块                                      |
+---------------------------------------------------------------+
```

**关键发现**：`samples` 目录下的 `.mflac` 与 P2P 缓存目录中的同名文件
（`D:\Temp\QQ_music_caches\downloadproxyNew\tp2p\.tpfs\duty\`）**头部完全一致，
仅差 192 字节（全在尾部）**。

```
samples\Billie Jean.mflac          = 68,108,035 字节
缓存\F0M0000Cc0LP1jd0bj.mflac     = 68,107,843 字节  (差 192)
```

验证方法：
```python
# a = samples 文件, b = 缓存文件
a.startswith(b)   # True —— 真实加密数据就是缓存文件本体
a[len(b):]        # 192 字节尾部块
```

## 1.1 音频质量等级与文件类型

| 质量 | 后缀 | 缓存前缀 | 输出格式 | 已验证 |
|------|------|---------|---------|--------|
| SQ（无损） | `.mflac` | `F0M...` / `Q0M...` | FLAC | ✅ |
| HQ（高品质） | `.mgg`（`_H`） | `O8M...` | Ogg | ✅ |
| 标准 | `.mgg`（`_L`） | `O4M...` | Ogg | ✅ |

- 文件名后缀：`_H` = HQ，`_L` = 标准（低），无后缀 = SQ
- 缓存前缀：`O4`/`O8`/`F0`/`Q0` 只是下载标识，**不区分加密算法**
- **三者加密算法完全相同**（同一个 `EncAndDesMediaFile` 路径），
  只是容器格式不同（FLAC vs Ogg）

## 2. 尾部 192 字节元数据块解析

```
偏移   内容
0x00  9e d0 04 00                    <- 未知字段（0x0004d09e）
0x04  02 00 00 00 05 00 00 00        <- 版本/标志
0x0c  "002P5kP80d88Vp"  UTF-16LE     <- 歌曲 ID
0x2c  "F0M0000Cc0LP1jd0bj.mflac" UTF-16LE  <- P2P 缓存文件名
0x9c  ...00 填充...
0xa8  81 6c 96 aa                    <- 校验值（非 CRC32，未识别）
0xac  c0 00 00 00
0xb0  01 00 00 00
0xb4  "musicex\0"                    <- 标记字符串
```

**结论**：该块是下载器附加的元数据，**不是解密密钥**，解密时会被去除。
mflac 和 mgg 都有这个 192 字节尾部块，结构一致。

## 3. 缓存目录结构（重要线索源）

```
D:\Temp\QQ_music_caches\
├── downloadproxyNew\tp2p\.tpfs\duty\
│   ├── F0M0000Cc0LP1jd0bj.mflac\    <- 每个文件一个目录
│   │   ├── F0M0000Cc0LP1jd0bj.mflac <- 实际加密数据
│   │   ├── .property
│   │   └── tp
│   ├── O4M0003KO0tp0otHSL.mgg\      <- O4M = 标准品质 mgg
│   └── O8M0000ZHHSQ0uQVlA.mgg\      <- O8M = HQ 品质 mgg
├── Log\QQMusic\*.log
└── WebkitCache\
```

- `.mflac` = 加密 FLAC；`.mgg` = 加密 Ogg；两者 EncType 均为 2
- 缓存文件名 `F0M0000Cc0LP1jd0bj.mflac` 会出现在 samples 文件的尾部元数据块中
- 这是判断"samples 文件 = 缓存文件 + 元数据块"的直接证据
- **缓存前缀 O4/O8/F0/Q0 仅是下载批次标识，不代表加密算法差异**

## 4. 头部特征

```
Billie Jean.mflac 头部 64 字节:
52 79 17 71 49 67 56 45 63 30 77 6a 53 72 de 43
12 d2 3b f3 47 31 6f a7 3e 1d 6d 86 f8 36 52 ce
...

You Are Not Alone.mflac 头部 64 字节:
0a 0a 55 73 4d 39 4f 14 49 53 24 48 42 4f ec 49
61 93 62 8d 49 3c 31 92 bc 80 fb b6 28 55 5a f8
...
```

- 不同文件头部不同 → 密钥是每文件独立的
- 头部前 128 字节 base64 字符占比高达 102/128（伪装成 base64），
  但解码失败 → 是加密数据碰巧密集落在 base64 字符集，不是真 base64
- 数据区熵 ≈ 7.95（高熵，符合流加密特征）
- 与 `fLaC` XOR 得到 `34 35 76 32` = "45v2"（无直接意义，仅巧合）

## 5. 常见误区（踩坑记录）

1. ❌ 误以为头部是 base64 密钥 → 实际头部就是加密数据
2. ❌ 误以为尾部 4 字节是 keylen → ReadEncKey 读的是文件尾 `-4` 处 4 字节，
   但对 samples 文件该值不合法，密钥读取逻辑需结合 Open 内部流程理解
3. ❌ 误以为 `musicex` 标记在 DLL 中是解密配置 → 实际是尾部元数据块
4. ❌ 误以为 `_L.mgg`（标准）与 `_H.mgg`（HQ）加密不同 → 实测同一算法，
   "Open 失败"实为**文件名编码损坏**（见 03 文档 §7）
5. ❌ 误以为 GetEncType 按文件头魔数判断 → 实际按**扩展名**匹配
   （`.mflac`/`.mgg`/`.mmp4` → EncType=2，见 02 文档 §4）
